# Getting Started

This guide walks through setting up a local development environment for CrypTransfer, a
Flutter (Material 3) application for secure, end-to-end encrypted file transfers backed by
Firebase (Authentication, Firestore, Storage).

## Prerequisites

- **Flutter SDK** `>=3.44.0` and **Dart SDK** `^3.12.0` (declared in `pubspec.yaml`)
- **Android Studio** with the Android SDK installed (for building/running on Android)
  - **Java 17** (the project's Gradle/Kotlin toolchain requires Java 17 — see
    `docs/configuration/overview.md`)
- An **Android emulator** or physical Android device with **USB debugging** enabled
  (the project is primarily developed/tested for Android; iOS/macOS/Web/Windows Firebase
  configurations also exist in `lib/firebase_options.dart` but are not the primary target)
- **Git** for cloning the repository
- A **Firebase project** with Authentication, Firestore, and Storage enabled

## Install Dependencies

Fetch all Dart/Flutter package dependencies declared in `pubspec.yaml`:

```bash
flutter pub get
```

This installs the Firebase packages (`firebase_core`, `firebase_auth`, `cloud_firestore`,
`firebase_storage`), cryptography (`pointycastle`, `flutter_secure_storage`), file handling
(`file_picker`, `path_provider`, `open_file`), and UI/auth dependencies (`google_fonts`,
`fl_chart`, `local_auth`, `provider`, `google_sign_in`).

## Firebase Setup

CrypTransfer initializes Firebase at startup in `lib/main.dart` using
`DefaultFirebaseOptions.currentPlatform`, which is defined in `lib/firebase_options.dart`.
This file (along with `android/app/google-services.json`) is generated by the FlutterFire CLI
and is already present in the repository, configured against the `cryptransfer-96e9f` Firebase
project.

For most local development, **no additional Firebase setup is required** — `flutter pub get`
followed by `flutter run` will connect to the existing project's Firestore, Auth, and Storage.

If you need to point the app at a different Firebase project (e.g. your own development
project), regenerate the configuration with the FlutterFire CLI:

```bash
firebase login
flutterfire configure
```

This regenerates `lib/firebase_options.dart` and `android/app/google-services.json` for the
selected project. See `docs/configuration/overview.md` for full details on:

- Firestore security rules (`firestore.rules`) and how to deploy them
  (`firebase deploy --only firestore:rules`)
- The `android/key.properties` file required for signed release builds (git-ignored, optional
  for `flutter run` debug builds — falls back to debug signing automatically)
- Service account setup for the maintenance scripts under `scripts/`

## Running the App

### On an emulator or connected device

1. Start an Android emulator (via Android Studio's Device Manager) or connect a physical device
   with USB debugging enabled.
2. Verify the device is detected:

   ```bash
   flutter devices
   ```

3. Run the app in debug mode:

   ```bash
   flutter run
   ```

This builds and installs a debug build (falling back to debug signing since
`android/key.properties` is git-ignored and typically absent on a fresh clone).

### Release build

```bash
flutter build apk --release
```

Uses `android/key.properties` for signing if present; otherwise falls back to debug signing
(see `docs/configuration/overview.md` for setting up release signing).

## First-Run Expectations

On first launch, the app starts at `SplashScreen`
(`lib/presentation/auth/splash_screen.dart`), which routes to onboarding/login/registration
screens (`lib/presentation/auth/`):

1. **Authentication** — Sign up or sign in via Firebase Authentication (email/password and
   Google Sign-In are configured via `firebase_auth` and `google_sign_in`).
2. **RSA key pair generation** — On first use of the receiver flow, an RSA key pair is generated
   off the UI isolate via `compute()` and the private key is stored locally using
   `flutter_secure_storage`. The public key is published to Firestore only when the user
   explicitly initiates a handshake (receiver-authorized handshake model — see
   `docs/architecture/overview.md`).
3. **Home screen** — After authentication, the home screen
   (`lib/presentation/home/`) provides access to sending files, receiving files (the "mailbox"
   toggle), finding/connecting with other users, and (for accounts with `isAdmin: true` in
   Firestore) the Admin Dashboard.
4. **No keys are exchanged automatically** — a receiver must explicitly open their mailbox and
   select a sender before any RSA public key or file data is transferred. This is the
   "Closed Mailbox" session model described in `docs/architecture/overview.md`.
