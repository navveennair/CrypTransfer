[492]: 4.4   Database Design

[493]: The schema enlists five fundamental tables, such as User, TransferSession, File, RSAKeys and AESKey. The User table stores user credentials including userID (PK), username, password, email, and role. The TransferSession table tracks every transfer transaction with sessionID (PK), senderID (FK), receiverID (FK), and a timestamp. File stores metadata about each moved item including fileID (PK), fileName, fileSize, fileType, and filePath, and contains a transferSessionID (FK) linking it to its parent session. RSAKeys contains the RSA key pair consisting of keyID (PK), userID (FK), publicKeyID, and privateKeyID, and refers to the TransferSession. The symmetric key used to encrypt the file contents is stored in the AESKey table, which includes aesKeyID (PK), userID (FK), and transferSessionID (FK).

[495]: Figure 4.21 Database Design for CrypTransfer system

[496]: The User class is associated with the TransferSession class through a 1-to-1 relationship where a User initiates a TransferSession. The foreign keys senderID and receiverID in the TransferSession table refer to the User model, allowing the system to track participants in each transfer instance.

[497]: The TransferSession class encapsulates a single-file transfer event. It contains a File record through a 1-to-1 relationship, where the File table has a backreference (transferSessionID) to its parent session. This ensures that every file is linked to exactly one transfer session for precise tracking.

[498]: There is a relationship between the User object and the RSAKeys table through the userID foreign key. A single User generates 0..* RSAKeys pairs. This relationship allows users to maintain unique cryptographic identities for different sessions, ensuring data security through appropriate key management.

[499]: The TransferSession class uses the RSAKeys table in a 1-to-1 relationship. The RSA keys associated with the session are used to securely exchange and encrypt the AES key. This setup ensures that the AES key used to encrypt a file is only accessible to the authorized receiver.

[500]: The AESKey table is encryptedBy the RSAKeys table in a 1-to-1 relationship. The receiver uses their private RSA key to decrypt the AES key, which then allows for the decryption of the file contents. This multi-layered encryption approach is central to the system's security.

[501]: The File table is encryptedWith the AESKey table. The aesKeyID is placed as a foreign key in the AESKey table (associated with the file and session), ensuring that the specific symmetric key used for the file contents is correctly mapped and retrievable.

[502]: The AESKey class is associated with the User class through a 1-to-1 relationship (User create AESKey). Every user is responsible for the creation of the symmetric key used in their outgoing transfers, ensuring that encryption occurs at the edge before data transmission.

[503]: Finally, the interconnected relationships between User, TransferSession, File, RSAKeys, and AESKey provide a safe and traceable transfer protocol. The ERD supports the secure hybrid encryption process, session handling, and non-repudiation requirements of the entire system.

[507]: 4.6    Chapter Summary

[508]: In this Chapter a design and requirement analysis for CrypTransfer (secure peer-to-peer file transfer) was introduced. It brought you UML diagrams to visualize interaction, data flow, and business processes. The design Key entities in the class diagram such as User, File, TransferSession, RSAKeys, AESKey demonstrate how the encryption and session handling are organized. Sequence diagrams specified processes such as login, file encryption, key generation, transfer, and cleanup and described ways to operate safely in the context of sessions. CrypTransfer uses a hybrid encryption, AES-256 as for the file encryption and RSA for the key exchange. The transport Layer Security protocol is used to keep the transmitted data secure and threaten attacks such as MITM. Each session has unique key pairs to provide traceability and confidentiality. Transient data is erased from memory post-decryption, to prevent remanence. The foreign keys are also exploited to connect all encryption ‘goodies’ in the database schema, thereby enforcing access control and data integrity as well. In Figma, interface designs that emphasise usability and secure workflow and access to non-technical users at login, through the encryption, on through file management and key handling. P2P architecture, the system implemented a peer-to-peer network to facilitate end-to-end encrypted communications that took the middleman (the server) out of the loop and increases privacy and security compared to traditional, server-dependent IM systems.
