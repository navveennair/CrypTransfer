## Summary

This phase upgrades the identity and networking layers to professional standards across five distinct sub-features. The codebase is well-structured — `ThemeService` already exists as a `ChangeNotifierProvider`, `AuthRepository` is injectable with mocked dependencies, and `SidebarDrawer` provides the natural insertion point for My Connections. The largest surface area is the `google_sign_in` package which jumped from v6 to v7 with breaking API changes: the old `signIn()` is replaced by the singleton `GoogleSignIn.instance.authenticate()` with separated authorization scope flow.

The existing `KeyRepository` uses sub-collections (`users/{uid}/connections`, `users/{uid}/friend_requests`) for the friendship model. The phase replaces this with a top-level `friendships` collection using deterministic docIds. The Disconnect operation must clean both `friendships` and `handshakes` (which is what the codebase calls `rsa_key_transfers`). The CONTEXT.md spec says `rsa_key_transfers` but the actual collection constant in `firebase_constants.dart` is `FirebaseConstants.handshakes = 'handshakes'`.

The `ThemeService` (`lib/core/utils/theme_service.dart`) is already wired into `main.dart` via `ChangeNotifierProvider` and the `MaterialApp.themeMode` reads from it. The theme onboarding overlay needs only to call `ThemeService.setThemeMode()` — the propagation is already handled.

**Primary recommendation:** Add `google_sign_in: ^6.2.0` (not v7) to align with the v6-era FlutterFire Auth documentation pattern that the CONTEXT.md locked decision describes. If the project requires v7, expect significant API changes (singleton, initialize(), authenticate(), separated authorization). The plan should pick one version and document the exact auth integration flow.

## Critical Discovery: google_sign_in Version Conflict

**The CONTEXT.md locked decision describes the v6 API pattern** (`GoogleSignIn().signIn()` returning a nullable `GoogleSignInAccount`). The current pub.dev latest is **v7.2.0** which has breaking changes:

| Feature | v6 API (locked in CONTEXT.md) | v7 API (current pub.dev) |
|---------|-------------------------------|--------------------------|
| Instance | `GoogleSignIn()` constructor | `GoogleSignIn.instance` singleton |
| Init | Not required | `await GoogleSignIn.instance.initialize()` (must call in main()) |
| Sign-in | `await GoogleSignIn().signIn()` → nullable | `await GoogleSignIn.instance.authenticate()` → throws on cancel |
| Access token | `googleAuth.accessToken` | `await googleUser.authorizationClient.authorizeScopes([...])` → `.accessToken` |
| idToken | `googleAuth.idToken` | `googleUser.authentication.idToken` (synchronous) |
| Null safety | Returns null on cancel | Throws `GoogleSignInException` on cancel |

**Recommendation:** Use `google_sign_in: ^6.2.0` to match the CONTEXT.md locked API pattern. This is the last stable v6 series. If the project wants the latest, use v7.2.0 and update the auth flow accordingly. The plan must pick one — do not mix API patterns.

### Pattern 1: Google Sign-In (v6 API — matches CONTEXT.md locked decision)
**What:** Call GoogleSignIn().signIn() to get a GoogleSignInAccount, then convert to Firebase credential.
**When to use:** On login and register screen "Continue with Google" tap.
```dart
// Source: FlutterFire docs + CONTEXT.md locked decision (v6 pattern)
Future<UserCredential?> signInWithGoogle() async {
  try {
    final GoogleSignInAccount? googleUser = await GoogleSignIn().signIn();
    if (googleUser == null) return null; // user cancelled
    
    final GoogleSignInAuthentication googleAuth =
        await googleUser.authentication;
    
    final credential = GoogleAuthProvider.credential(
      accessToken: googleAuth.accessToken,
      idToken: googleAuth.idToken,
    );
    
    final userCredential =
        await _auth.signInWithCredential(credential);
    
    // Create users doc if new account
    final uid = userCredential.user!.uid;
    final userDoc = await _db.collection('users').doc(uid).get();
    if (!userDoc.exists) {
      await _db.collection('users').doc(uid).set({
        'email': googleUser.email,
        'displayName': googleUser.displayName ?? googleUser.email,
        'photoURL': googleUser.photoUrl,
        'createdAt': FieldValue.serverTimestamp(),
        'isAdmin': false,
        'isReadyToReceive': false,
      });
    }
    return userCredential;
  } on FirebaseAuthException catch (e) {
    throw AuthException(_mapGoogleAuthError(e.code));
  }
}
```

### Pattern 4: Disconnect Batch Delete
**What:** Atomic delete of friendship + cleanup of handshake docs.
**When to use:** "Disconnect" button in ConnectionsScreen.
```dart
// Source: derived from existing closeReceiverSession batch pattern in EncryptionService
Future<void> disconnect(String friendUid) async {
  final docId = friendshipDocId(_uid, friendUid);
  final batch = _db.batch();
  
  // 1. Delete friendship document
  batch.delete(_db.collection('friendships').doc(docId));
  
  await batch.commit();
  
  // 2. Delete handshakes (2 queries — batch has 500-write limit but this is small)
  final q1 = await _db.collection(FirebaseConstants.handshakes)
      .where('receiverId', isEqualTo: _uid)
      .where('senderId', isEqualTo: friendUid)
      .get();
  final q2 = await _db.collection(FirebaseConstants.handshakes)
      .where('senderId', isEqualTo: _uid)
      .where('receiverId', isEqualTo: friendUid)
      .get();
  final cleanBatch = _db.batch();
  for (final doc in [...q1.docs, ...q2.docs]) {
    cleanBatch.delete(doc.reference);
  }
  await cleanBatch.commit();
}
```

### Anti-Patterns to Avoid
- **Using GoogleSignIn.instance singleton (v7) when google_sign_in: ^6 is declared:** v6 uses `GoogleSignIn()` constructor. Mixing APIs causes `NoSuchMethodError` at runtime.
- **Querying friendships with TWO arrayContains on same field:** Firestore does not support `arrayContains` + `arrayContains` on the same field. The `participants` design with one `arrayContains` + equality `status` filter is correct — but needs the composite index.
- **Writing the theme onboarding dialog to Firestore synchronously and blocking navigation:** Firestore write is fire-and-forget. Do not await it in the critical path.
- **Calling `_formKey.currentState!.validate()` before checking `mounted`:** LoginScreen calls setState in async context; always check `mounted` before form actions.
- **Using `users/{uid}/connections` sub-collection for the new friend model:** The old sub-collection model (`KeyRepository.acceptConnectionRequest`) uses `users/{uid}/connections`. The new `friendships` top-level collection is separate. Do NOT delete the old sub-collection data; the transfer rules in `firestore.rules` still reference it as a fallback for transfer authorization.

## Common Pitfalls

### Pitfall 1: google_sign_in v7 API on v6 Pubspec
**What goes wrong:** If developer copies v7 code examples (with `GoogleSignIn.instance`, `authenticate()`, `authorizationClient`) but pubspec pins v6, the code compiles but throws `MissingPluginException` or `NoSuchMethodError` at runtime.
**Why it happens:** v7 is a breaking change with new singleton pattern; training data and many tutorials mix v6 and v7 examples.
**How to avoid:** Check `pubspec.lock` after `flutter pub get` to confirm actual resolved version. Use v6 API if pubspec pins `^6.x`.
**Warning signs:** `MissingPluginException` for google_sign_in, or `The getter 'instance' isn't defined` compile error.

### Pitfall 2: Composite Index Missing for friendships Query
**What goes wrong:** `where('participants', arrayContains: uid).where('status', isEqualTo: 'accepted')` throws a Firestore `failed-precondition` error in production with "The query requires an index."
**Why it happens:** Firestore auto-creates single-field indexes but NOT composite indexes for `arrayContains` + equality on a different field.
**How to avoid:** Add the composite index to `firestore.indexes.json` and deploy with `firebase deploy --only firestore:indexes` before or alongside the code deployment. The error message in Firestore logs contains a direct link to create it via the Firebase console.
**Warning signs:** Query works in emulator (emulator auto-creates indexes) but fails in production.

### Pitfall 3: Theme Onboarding Race Condition
**What goes wrong:** Theme dialog shows briefly then disappears because `Navigator.pushAndRemoveUntil` fires before the dialog is dismissed.
**Why it happens:** `_checkAndShowThemeOnboarding` is called async but navigation might not await the dialog close.
**How to avoid:** `await showDialog(...)` before calling `Navigator.pushAndRemoveUntil`. The dialog must be dismissed BEFORE navigating to HomeScreen.
**Warning signs:** HomeScreen appears behind dialog, or dialog dismisses instantly.

### Pitfall 4: Disconnect Deletes Wrong handshakes Collection
**What goes wrong:** Disconnect targets `rsa_key_transfers` (per CONTEXT.md wording) but the Dart constant is `FirebaseConstants.handshakes = 'handshakes'`.
**Why it happens:** CONTEXT.md and the old codebase used the term `rsa_key_transfers` interchangeably with `handshakes`. The actual Firestore collection name is `handshakes`.
**How to avoid:** Always use `FirebaseConstants.handshakes` constant; never hardcode `'rsa_key_transfers'`.
**Warning signs:** Disconnect appears to succeed but sender sees stale "Secure Channel Established" badge.

### Pitfall 5: Google Sign-In Users Lack username Field
**What goes wrong:** The `users` doc for a Google user lacks the `username` field. Code that reads `data['username']` returns null, causing `KeyRepository.searchUsers` and `SenderScreen` greeting to show "Unknown".
**Why it happens:** `AuthRepository.register()` sets `username` explicitly. Google sign-in creates a doc with `displayName` but no `username`.
**How to avoid:** On first Google sign-in, also write `username: googleUser.displayName?.replaceAll(' ', '_').toLowerCase() ?? uid` (or prompt user to choose a username). CONTEXT.md spec says `displayName` — confirm if `username` field is needed or if `displayName` is sufficient for this phase.
**Warning signs:** `KeyRepository.searchUsers` returns empty for Google-signed users; SenderScreen shows "Unknown".

### Pitfall 6: LoginScreen Uses TextField, Not TextFormField
**What goes wrong:** Adding `GlobalKey<FormState>` and calling `_formKey.currentState!.validate()` has no effect because existing login fields are `TextField` not `TextFormField`.
**Why it happens:** LoginScreen was built with manual validation logic, not Flutter's Form system.
**How to avoid:** Migrate both `TextField` widgets in LoginScreen to `TextFormField` with `validator` callbacks when wrapping in `Form`. RegisterScreen already uses a custom validation pattern — keep its existing pattern and add the new strength rules.
**Warning signs:** `_formKey.currentState!.validate()` always returns `true`.

### Firestore Rules for friendships Collection
```javascript
// Add to firestore.rules inside the main match block
match /friendships/{friendshipId} {
  // Participants can read their own friendship docs
  allow read: if isAuthenticated() &&
                 request.auth.uid in resource.data.participants;
  
  // Either participant can create a friendship request
  allow create: if isAuthenticated() &&
                   request.auth.uid in request.resource.data.participants &&
                   request.resource.data.participants.size() == 2;
  
  // Either participant can update status (accept, block)
  allow update: if isAuthenticated() &&
                   request.auth.uid in resource.data.participants;
  
  // Either participant can delete (disconnect)
  allow delete: if isAuthenticated() &&
                   request.auth.uid in resource.data.participants;
}
```

### FriendshipModel
```dart
// lib/data/models/friendship_model.dart
class FriendshipModel {
  final String docId;
  final List<String> participants;
  final String status; // 'pending' | 'accepted' | 'blocked'
  final String requesterId;
  final Timestamp? createdAt;

  FriendshipModel.fromDoc(DocumentSnapshot doc)
    : docId = doc.id,
      participants = List<String>.from(doc['participants'] ?? []),
      status = doc['status'] as String? ?? 'pending',
      requesterId = doc['requesterId'] as String? ?? '',
      createdAt = doc['createdAt'] as Timestamp?;

  String friendUid(String myUid) =>
```

## State of the Art

| Old Approach | Current Approach | When Changed | Impact |
|--------------|------------------|--------------|--------|
| `GoogleSignIn()` constructor per-call | `GoogleSignIn.instance` singleton + `initialize()` | google_sign_in v7.0.0 | Must call `initialize()` in `main()` before any auth |
| `signIn()` returns nullable on cancel | `authenticate()` throws `GoogleSignInException` on cancel | google_sign_in v7.0.0 | Requires try/catch instead of null check |
| `SharedPreferences.getInstance()` everywhere | `SharedPreferencesAsync` / `SharedPreferencesWithCache` (recommended for new code) | shared_preferences 2.x | Legacy API still works; ThemeService already uses it; no migration needed |
| Sub-collection friend model (`users/{uid}/connections`) | Top-level `friendships` collection with arrayContains | This phase | Enables single query across both directions; requires composite index |

**Deprecated/outdated in this codebase:**
- `KeyRepository.getConnectedFriends()`: Uses old sub-collection model. Will be superseded by `FriendshipRepository.streamAcceptedFriends()`. Keep old code — it's referenced by `resyncPublicKeyToAllConnections()` which is not touched in this phase.
- `KeyRepository.getConnectionStatus()`: Queries old sub-collection model. The new `FriendshipRepository` should be used for connection status checks in FindFriendsScreen going forward.

## Open Questions

1. **Google Sign-In: v6 vs v7?**
   - What we know: CONTEXT.md describes v6 API pattern (`GoogleSignIn().signIn()`); current pub.dev latest is v7.2.0 with breaking changes
   - What's unclear: Whether the project wants the latest package or wants to match the CONTEXT.md locked API pattern
   - Recommendation: Default to v6.2.0 per CONTEXT.md; document v7 path as alternative in the plan for planner to surface to user

2. **Google Sign-In users and the `username` field**
   - What we know: `AuthRepository.register()` writes `username` field; Google sign-in doc spec in CONTEXT.md does NOT include `username`
   - What's unclear: Whether `username` is required for Google users or if `displayName` suffices for all places that read `data['username']`
   - Recommendation: Write `username` as `displayName?.replaceAll(' ', '_')` on first Google sign-in to avoid nulls in existing code that reads `data['username']`

3. **SHA-1 fingerprint for Google Sign-In on Android**
   - What we know: Firebase project has a `google-services.json`; google_sign_in on Android needs the debug AND release SHA-1 registered in Firebase console
   - What's unclear: Whether debug SHA-1 is already registered (likely yes if Firebase was set up) and whether release SHA-1 from `android/key.properties` is registered
   - Recommendation: Plan task to verify SHA-1 in Firebase console; document `keytool -list -v -keystore` command as part of setup verification

4. **FindFriendsScreen friend request integration with new friendships model**
   - What we know: `FindFriendsScreen` calls `KeyRepository.sendConnectionRequest()` which writes to old sub-collection
   - What's unclear: Whether to update `FindFriendsScreen` to write to the new `friendships` collection in this phase
   - Recommendation: Yes — update `_sendRequest()` to write to `friendships` in this phase; otherwise the My Connections screen will show no friends

### Known Threat Patterns for this Stack

| Pattern | STRIDE | Standard Mitigation |
|---------|--------|---------------------|
| Friendship doc spoofing (writing other users' participant pair) | Tampering | Firestore rule: `request.auth.uid in request.resource.data.participants` |
| Disconnect by non-participant | Tampering | Firestore rule: `request.auth.uid in resource.data.participants` on delete |
| Google ID token replay | Spoofing | Firebase Auth handles token validation server-side; never log or store raw idToken |
| Mass friend request spam | DoS | No rate limiting in Firestore rules (accepted risk for thesis scope) |
| Theme preference poisoning via Firestore | Tampering | Firestore users/{uid} update rule: `isOwner(userId)` already enforces owner-only write |

**SecurityLifecycleMixin:** The `ConnectionsScreen` must apply `SecurityLifecycleMixin` (per CLAUDE.md: "Applied to: SenderScreen, ReceiverScreen, TransferProgressScreen, DownloadConfirmScreen, EndSessionScreen, DecryptScreen"). The ConnectionsScreen does not handle key material so the mixin is defensive but follows project convention.
