<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| HomeScreen → SenderScreen | preFilledPartnerUid is caller-supplied; must be a valid partner UID from a connected neutral_handshakes doc |
| HomeScreen → ReceiverScreen | preFilledSenderUid is caller-supplied; same trust boundary |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-03-01 | Spoofing | SenderScreen preFilledPartnerUid | accept | The param is populated by HomeScreen from a Firestore doc the user is a party to (proposerId or partnerId). HomeScreen does not accept arbitrary input — it reads from the stream. The pre-fill param carries no cryptographic authority; the actual RSA key still arrives via `streamHandshakesForSender()` (verified against receiverId). |
| T-05-03-02 | Spoofing | ReceiverScreen preFilledSenderUid | accept | Same rationale as T-05-03-01. Pre-fill only auto-calls `_onSenderSelected()` — the actual handshake and key exchange proceed through the existing `selectSenderHandshake()` Firestore write, which is rule-protected. |
| T-05-03-03 | Tampering | _onHandshakeUpdate receiver-ID filter | mitigate | The new guard `widget.preFilledPartnerUid == null || receiverId == widget.preFilledPartnerUid` prevents a different receiver's RSA key from being accepted when a specific partner is pre-filled. Without this guard, a malicious receiver could publish a key and have it accepted. |
</threat_model>
