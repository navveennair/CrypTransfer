Exact text to insert:
```javascript

    // ─── neutral_handshakes ──────────────────────────────────────────────────
    // Connection-layer neutral handshakes. Separate from session-layer `handshakes`.
    // proposer creates; both parties read; only partner may accept/reject;
    // proposer's own doc may also be marked connected (mutual-accept WriteBatch);
    // either party may delete (cancel or post-session cleanup).
    match /neutral_handshakes/{handshakeId} {
      allow read: if isAuthenticated() &&
                     (resource.data.proposerId == request.auth.uid ||
                      resource.data.partnerId == request.auth.uid);

      // Only proposer may create, and only with their own UID as proposerId
      allow create: if isAuthenticated() &&
                       request.resource.data.proposerId == request.auth.uid;

      // Partner may accept or reject; proposer's own doc may be marked connected
      // by a mutual-accept WriteBatch (proposer cannot reject their own proposal)
      allow update: if isAuthenticated() && (
        (resource.data.partnerId == request.auth.uid &&
         request.resource.data.status in ['connected', 'rejected'])
        ||
        (resource.data.proposerId == request.auth.uid &&
         request.resource.data.status == 'connected')
      );

      // Either party may delete (cancel proposal or post-session cleanup)
      allow delete: if isAuthenticated() &&
                       (resource.data.proposerId == request.auth.uid ||
                        resource.data.partnerId == request.auth.uid);
    }
```

Do NOT modify any existing rules. Do NOT remove or alter the `handshakes` block. Only insert the new block.

Verify the dual `allow update` condition is present — it is required for the mutual-accept WriteBatch (Pitfall 4 from RESEARCH.md). Without the second clause (`proposerId == request.auth.uid && status == 'connected'`), the acceptor cannot update the `B_A` doc (their own outgoing proposal) to connected.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client Dart → Firestore | Unauthenticated or wrong-identity writes to neutral_handshakes blocked by rules |
| proposerId field | User should only create docs where proposerId == their own UID |
| status field | Only two valid status transitions: pending→connected, pending→rejected |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-02-01 | Spoofing | neutral_handshakes create | mitigate | Firestore rule: `request.resource.data.proposerId == request.auth.uid` — proposer cannot spoof another user's UID as proposerId |
| T-05-02-02 | Elevation of Privilege | neutral_handshakes update (self-accept) | mitigate | Firestore rule: update requires `resource.data.partnerId == request.auth.uid` for accept/reject; a user cannot accept their own proposal (proposerId != partnerId by design; create rule blocks same-party docs) |
| T-05-02-03 | Tampering | neutral_handshakes status field | mitigate | Firestore rule: `request.resource.data.status in ['connected', 'rejected']` whitelist; arbitrary strings are rejected |
| T-05-02-04 | Information Disclosure | neutral_handshakes read | mitigate | Firestore rule: read requires `proposerId == auth.uid OR partnerId == auth.uid`; third parties cannot read connection docs |
| T-05-02-05 | Tampering | HandshakeRepository.sendProposal() | mitigate | Dart-layer guard: `partnerUid` non-null/non-empty assertion before Firestore write (add `if (partnerUid.isEmpty) throw AuthException('partnerUid required')` at top of method) |
| T-05-02-06 | Denial of Service | neutral_handshakes create spam | accept | No push notifications used; approval banners driven by Firestore stream (rate-limited by listener); no server-side rate limit added — acceptable for MVP |
