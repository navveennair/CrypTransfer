- [x] **CONSTRAINT: Document ID Collision** — Both `neutral_handshakes` and `handshakes` collections can write to overlapping docs when roles reverse due to sorted UID scheme. This causes last-writer-wins overwrite without atomic protection.

## Context & Mental Model

**The Core Issue (Now Solved):**
Hook 1 (connection) uses directional doc IDs (`a_b` always means A→B), but Hook 2 (transfer roles) was using non-directional IDs (`a_b` is just lowercase sort of pair). When roles reverse (proposer becomes receiver), the same doc gets overwritten, breaking stream listeners and causing race conditions.

**Why Fix 2 Works:**
- Each transfer session now gets a unique Firestore auto-ID (not based on user pair)
- Session A→B creates doc "auto-id-123" with roles A→sender, B→receiver
- Session B→A (reversed roles) creates doc "auto-id-456" with roles B→sender, A→receiver
- No collision: different docs, different IDs, stream queries find the right one via `senderId` field

**Why Fixes 3 & 4 Are Not Needed:**
- Fix 3 (transaction): Prevents duplicate role assignments, but Fix 2's unique IDs already prevent collision
- Fix 4 (no merge:true): Prevents partial overwrites, but cross-session contamination is already eliminated by unique IDs

**Next Steps (Decision Point):**
1. **Proceed directly to UAT testing** — Validate Fix 1+2 solve the architectural problem, skip optional hardening
2. **Implement Fix 3 & 4 first** — Add transaction-level safety and remove merge:true as defensive best-practices
3. **Implement only Fix 3 or 4** — Pick one for additional hardening

Recommendation: UAT first. If tests pass, the architectural fixes are sufficient. If issues arise, diagnosis will guide what's needed.
