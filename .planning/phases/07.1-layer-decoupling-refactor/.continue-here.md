# BLOCKING CONSTRAINTS — Read Before Anything Else

> These constraints were discovered through direct code analysis of the conflict audit.
> Each one MUST be understood before proceeding with remaining fixes.

- [ ] **CONSTRAINT: Document ID Collision** — Both `neutral_handshakes` and `handshakes` collections can write to overlapping docs when roles reverse due to sorted UID scheme. This causes last-writer-wins overwrite without atomic protection.
  - **Mitigation required:** Fix 2 (non-deterministic doc ID) OR Fix 3 (atomic transaction lock) must succeed before UAT testing

- [ ] **CONSTRAINT: Stream Query Staleness** — SenderScreen listens to `handshakes WHERE senderId == currentUser`. If partner overwrites roles, document disappears from sender's stream, breaking transfer flow.
  - **Mitigation required:** Fix 2 or Fix 3 must guarantee role fields are not overwritten after initial assignment

- [ ] **CONSTRAINT: No Connection Validation** — assignTransferRole() had no check that connection exists before role assignment. Fix 1 adds validation but must be verified to compile and not break existing flows.
  - **Mitigation required:** Compile-check Fix 1 in next session before proceeding

- [ ] **CONSTRAINT: merge:true Vulnerability** — SetOptions(merge: true) allows partial field overwrites instead of atomic assignment. Fix 4 (remove merge for role fields) must be applied AFTER Fixes 2/3 to avoid cascading changes.
  - **Mitigation required:** Implement Fix 4 last, after atomic assignment is guaranteed

**Do not proceed with Fixes 2-4 until all boxes are checked and fixes are understood.**

## Critical Anti-Patterns

| Pattern | Description | Severity | Prevention Mechanism |
|---------|-------------|----------|---------------------|
| Deterministic doc ID for bidirectional ops | Using sorted UID scheme for multi-role scenarios creates collision risk when roles reverse. Both users can write same doc with conflicting roles. | blocking | Fix 2: Use unique transfer-session ID not based on UID pair, OR Fix 3: Use Firestore transaction to lock first writer |
| Partial overwrites with merge:true | SetOptions(merge: true) allows role fields to be selectively overwritten. Last writer wins without validation. | blocking | Fix 4: Use atomic set (no merge) for role fields, or use transaction to prevent overwrites |
| Post-navigation validation | Role conflict validation runs AFTER navigation to ReceiverScreen. Too late to prevent UI state corruption. | advisory | Validation in assignTransferRole() prevents invalid role pairs from being created in the first place |

## Context & Mental Model

The core issue: Hook 1 (connection) uses directional doc IDs (`a_b` always means A→B), but Hook 2 (transfer roles) uses non-directional IDs (`a_b` is just lowercase sort of pair). When roles reverse (proposer becomes receiver), the same doc gets overwritten, breaking stream listeners and causing race conditions.

**Why sequential fixes:**
- Fix 1 (validation) prevents invalid state upstream
- Fix 2 or 3 (deterministic ID or transaction) prevents collision
- Fix 4 (no merge) prevents partial overwrites
- Each fix must be verified independently before the next is implemented

**The architectural insight:** We need EITHER:
- A) Non-colliding doc IDs (unique per session) → Fix 2
- B) Atomic role locking (transaction guarantee) → Fix 3
- But NOT merge:true, which allows fields to be overwritten without validation
