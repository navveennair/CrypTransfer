## Deviations from Plan

### Rule 2 — Auto-fix Missing Critical Functionality

Added two repository methods not in Wave 0 specification:

1. **`AuthRepository.getIsReadyToReceive(uid)`**
   - Rationale: `receiver_screen.dart` line 178 reads user `isReadyToReceive` field; critical for UI decoupling
   - UserModel does not include this field; adding to AuthRepository (user profile operations) preserves separation of concerns
   - Returns `bool` with fallback to `false` on error

2. **`TransferRepository.watchPendingTransfersFromSender(receiverId, senderId)`**
   - Rationale: `receiver_screen.dart` line 327 filters pending transfers by specific sender; using generic `watchPendingTransfers()` would fire on any incoming transfer
   - Adding this method preserves the UI's current behavior (listen only for transfers from selected sender)
   - Implements the same Firestore query pattern but encapsulated in the repository

Both additions follow the "strict decoupling mandate" (CLAUDE.md) and Rule 2 (auto-fix missing critical functionality). They were necessary for achieving 100% migration without changing query semantics.

## Known Limitations

- **QuerySnapshot filtering:** `receiver_screen.dart` could theoretically use `watchPendingTransfers()` and filter on `senderId` in the StreamBuilder, but adding `watchPendingTransfersFromSender()` preserves original query semantics and avoids unnecessary Firestore reads for unrelated transfers
- **UserModel extension:** `receiver_screen.dart` reads `isReadyToReceive` but UserModel doesn't include this field; added method to AuthRepository rather than modifying the model to avoid tight coupling
