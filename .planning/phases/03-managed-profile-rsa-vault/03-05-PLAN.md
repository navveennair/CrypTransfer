<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Client → Firestore rsa_key_manager | Firestore rules enforce server-side immutability and ownership |
| Client → Firestore profile | Firestore rules enforce owner-only create/update |
| ReceiverScreen → Vault | Navigator.push; returns via pop; _checkKeyStatus() called on return |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-05-01 | Tampering | rsa_key_manager audit log mutation | mitigate | `allow update: if false` in Firestore rules makes every audit doc permanently immutable server-side. No client can overwrite or update an audit document. |
| T-03-05-02 | Tampering | rsa_key_manager create with invalid action | mitigate | `request.resource.data.action in ['generated', 'regenerated', 'deleted']` validates the action field server-side on every create. Any document with an unlisted action value is rejected. |
| T-03-05-03 | Elevation of Privilege | Another user reading rsa_key_manager docs | mitigate | `allow read: if isOwner(userId) || isAdmin()` — only the owning user and admins can read audit logs. |
| T-03-05-04 | Elevation of Privilege | Another user reading profile/preferences | mitigate | `allow read: if isOwner(userId) || isAdmin()` — same ownership pattern as audit logs. |
| T-03-05-05 | Tampering | profile/preferences update by non-owner | mitigate | `allow update: if isOwner(userId) || isAdmin()` — only owner or admin can update preferences. |
| T-03-05-06 | Tampering | rule conflict with audit_logs collection-group | accept | New `rsa_key_manager` block is inside `match /users/{userId}`, not a collection-group. The existing `/{path=**}/audit_logs` collection-group rule does not match `rsa_key_manager` paths — no conflict. |
  </threat_model>
