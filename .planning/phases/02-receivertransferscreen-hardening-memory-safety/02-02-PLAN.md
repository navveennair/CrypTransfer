<objective>
Eliminate the unregistered double plaintext copy on Android by changing `FilePicker.pickFiles(withData: true)` to `withData: !kIsWeb` in `SenderScreen._pickFile()`, and guard the cloud-URI edge case (null path AND null bytes).

Purpose: Today every file pick on Android loads the entire plaintext into `PlatformFile.bytes` — a `Uint8List` that is **not registered** with `SecurityLifecycleMixin` and therefore cannot be zeroed on wipe. Since `TransferService.resolve()` already reads via `openRead()` from `file.path` in 64 KB chunks on non-web platforms, the `bytes` copy is unused on Android. Dropping it removes an entire plaintext copy from the heap.

Output: Two-line `_pickFile()` modification plus a null-path SnackBar guard. All TC-WIPE tests remain green.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| FilePicker → Dart heap | The plaintext the user selects crosses into `PlatformFile.bytes` if `withData: true`; this Uint8List is NOT registered with SecurityLifecycleMixin and cannot be wiped. Eliminating the copy on non-web closes that gap. |
| Content provider (Android SAF) → app | Cloud-URI pickers (Google Drive, Gmail, Files by Google) can return a PlatformFile with null path, violating the "path is available" invariant the MEM-01 change relies on. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-08 | Information Disclosure | `PlatformFile.bytes` holds an unregistered, un-wipeable copy of the user's plaintext on Android — lingers on the heap until garbage collection and is visible to a rooted-device memory inspection / core-dump attacker | mitigate | MEM-01 / D-12: `withData: kIsWeb` ensures bytes is null on Android. `TransferService.resolve()` reads the file via path-based 64 KB chunks which flow through registered buffers inside `_encryptFile`. |
| T-02-09 | Denial of Service | Cloud-URI pick (Drive / Gmail) returns PlatformFile with null path AND null bytes, which after MEM-01 would cause `_encryptFile` to silently return, leaving the user with no feedback and a broken workflow | mitigate | D-13: Explicit null-path check in `_pickFile` surfaces a user-facing SnackBar `This file type isn't supported — try saving it locally first.` before `_encryptFile` is ever called. |
| T-02-10 | Tampering | Existing `_encryptFile` guard `if (file == null || file.bytes == null) return;` was safe under `withData: true` but becomes a silent no-op for every Android pick under `withData: kIsWeb`, effectively disabling file transfer on Android | mitigate | Edit 3: platform-aware guard (`if (kIsWeb && file.bytes == null) return; if (!kIsWeb && file.path == null) return;`) keeps web path functional and non-web path flowing through TransferService.resolve. |
| T-02-11 | Information Disclosure | Switching to `withData: kIsWeb` means web users keep the un-wipeable bytes buffer — web is technically still at risk | accept | FYP scope: browsers have no usable file path; without bytes there is no way to read the file on web. Browser-process sandboxing is the compensating control. Documented here; SEC-02 / future work may move web to a streaming Blob API. |
| T-02-12 | Repudiation | User who picks a cloud file receives the "try saving locally" SnackBar but no deeper diagnostic — may retry cloud pick and get the same message | accept | UX-affordance is the correct mitigation; logging to Firestore would violate the zero-telemetry principle of this app. |
</threat_model>
