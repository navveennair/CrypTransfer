## Interaction Contracts

These are the precise interaction flows for all four gaps. Executor uses these as the source of truth.

### Gap 1 — ReceiverScreen Back-Navigation Guard

```
User action                   canPop value           onPopInvokedWithResult branch
─────────────────────────────────────────────────────────────────────────────────
Back gesture / HW back btn
  _isReadyToReceive = true     false                 !didPop → check _sessionLocked first
  _isReadyToReceive = false
    _handshakeDocId != null    true                  didPop → clearTransferRoles()
    _handshakeDocId == null    true                  didPop → nothing (clean exit)

In !didPop branch (mailbox open):
  if (_sessionLocked)          —                     show SnackBar SB-01, no pop
  else if (_isReadyToReceive)  —                     call _showCloseSessionDialog()
                                                       .then((confirmed) {
                                                         if (confirmed && mounted)
                                                           _sessionManager.wipeSession(...)
                                                           Navigator.pop(context)
                                                       })
```

**Constraint:** `_showCloseSessionDialog()` must be called via `.then()`, NOT `await` — `onPopInvokedWithResult` is a synchronous `void` callback. Using `async`/`await` here returns a Future the framework ignores.

**Constraint:** `wipeSession()` must fire only AFTER dialog confirmation — it transitions `SessionState.terminated` immediately, triggering reactive EncryptionService cleanup.

**Animation:** None new. `_showCloseSessionDialog()` uses the existing `showModalBottomSheet` with its default enter/exit animation.

### Gap 2 — SenderScreen Stale Key Invalidation

```
Firestore stream fires (new publicKey in handshake doc)
  │
  ├─ mid-flight guard: if (_encrypting || _encryptingKey) return  (D-06)
  │
  ├─ capture: final previousPublicKey = _selectedReceiverPublicKeyJson  (BEFORE setState)
  │
  ├─ setState: _selectedReceiverPublicKeyJson = newPublicKey
  │
  └─ stale check:
       if (previousPublicKey != null
           && newPublicKey != previousPublicKey
           && _encryptedAESKey != null)
         _wipeSensitiveData()          (light wipe — D-07)
         show SnackBar SB-02
```

**What is preserved after light wipe:** `_file`, `_receiverId`, `_receiverUsername`, `_selectedReceiverPublicKeyJson` (now updated), receiver-ready state. User can immediately re-run Step 2 encryption without re-selecting a file or receiver.

**What is wiped:** `_encryptedBytes`, `_encryptedAESKey`, `_aesKey`, `_iv`. All `wipeAll()` registered buffers zeroed.

**No visual state change beyond:** (1) Step 2 CrypButton re-enables (because `_fileEncrypted` getter becomes false when `_encryptedBytes == null`), (2) SnackBar SB-02 appears.

### Gap 3 — SenderScreen Step 1 Re-Pick UX Lock

```
_fileEncrypted == false (initial state / after wipe):
  CrypButton "Browse Files"   → enabled  (onPressed: _receiverSelected ? _pickFile : null)
  "Change File" TextButton    → hidden   (not in widget tree)

_fileEncrypted == true (after Step 2 completes):
  CrypButton "Browse Files"   → disabled (onPressed: null → greyed by Material 3)
  "Change File" TextButton    → visible  (below _FileCard, color: cs.onSurfaceVariant)

User taps "Change File" TextButton:
  showDialog → AlertDialog
    Title:   "Change File?"
    Content: "This will wipe your encrypted data and AES key. Are you sure?"
    [Cancel]  → Navigator.pop(ctx)           (dialog dismissed, nothing else)
    [Confirm] → Navigator.pop(ctx)
               _wipeSensitiveData()           (light wipe)
               _pickFile()                    (opens file picker)
```

**Layout rule:** "Change File" TextButton appears with `SizedBox(height: 8)` above it (sm spacing), directly below `_FileCard`. It is centered or left-aligned matching the `_FileCard` alignment in context.

**Visibility driver:** `_fileEncrypted` getter (`_encryptedBytes != null`). No additional state variable needed.

### Gap 4 — ReceiverScreen Step 1 Lockout

```
_isReadyToReceive == false:
  Step 1 StepCard             → opacity 1.0, IgnorePointer(ignoring: false)
  AppBar settings IconButton  → onPressed: _openKeyManager  (active)

_isReadyToReceive == true:
  Step 1 StepCard             → opacity 0.4 (AnimatedOpacity, 300ms), IgnorePointer(ignoring: true)
  AppBar settings IconButton  → onPressed: null  (Material 3 auto-disables icon color)
```

**Animation:** `AnimatedOpacity(duration: const Duration(milliseconds: 300))` — matches existing step-gating duration throughout the screen.

**No SnackBar or tooltip** on tap when locked. The greyed-out visual is the full signal. The user understands they are in an active session.

## Anti-Patterns — Enforced for This Phase

These are explicitly prohibited for all four gaps (derived from RESEARCH.md anti-patterns section):

1. Do NOT place stale-key comparison inside `setState` callback — comparison must use value captured BEFORE `setState` call.
2. Do NOT use `async`/`await` inside `onPopInvokedWithResult` — use `.then()` to chain async dialog results.
3. Do NOT call `Navigator.pop()` when `didPop == true` — that would cause a double-pop.
4. Do NOT call `_revertToWaiting()` for the stale-key wipe (Gap 2) — D-07 mandates light wipe only (`_wipeSensitiveData()`); `_revertToWaiting()` would clear receiver connection and file.
5. Do NOT use a raw `ElevatedButton` or `OutlinedButton` for the "Change File" action — `TextButton` with `cs.onSurfaceVariant` is the correct subtle-action pattern.
6. Do NOT use `Opacity` widget as a wrapper for step lockout — use `AnimatedOpacity` to match the existing animated step-gating pattern.
7. Do NOT call `wipeSession()` before the confirmation dialog resolves — state transition to `terminated` fires the reactive EncryptionService cleanup chain immediately and is irreversible.
