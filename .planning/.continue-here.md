# BLOCKING CONSTRAINTS — Read Before Anything Else

> These were discovered through failure during this session.

- [x] **FIRESTORE SECURITY RULES ARE CRITICAL** — The friendships sub-collection writes were failing due to security rules blocking non-owner writes. This MUST be verified in production before merging any connection-related code.
- [x] **FAKEFIRESTOREDOES NOT ENFORCE SECURITY RULES** — Tests with FakeFirestore give false confidence. Always verify fixes with real Firestore or by reading the actual security rules file (`firestore.rules`).
- [x] **WRITEBATCH DOES NOT HAVE ALL-OR-NOTHING SEMANTICS FOR SECURITY** — When a WriteBatch write fails due to security rules, subsequent writes still execute. The first write can succeed while the second fails silently, leaving inconsistent state.

## What This Session Taught Us

**Key Learning:** Always check Firestore security rules when data isn't persisting, even if code looks correct. FakeFirestore tests don't catch security rule violations.

**Pattern to remember:** WriteBatch partial failures are silent — one write can succeed while another fails. Always verify both sides of a bidirectional operation.

**Next time:** When fixing "Connection not established" issues, immediately check:
1. Does the connection doc exist in Firestore?
2. Do the security rules allow the writes?
3. Is there a race condition where the read happens before the write completes?
